# اتصال API مباشر دون اسم دومين

Snapshot date: 2026-10-27

العنوان المعتمد لنسخة APK الجديدة هو `https://3.121.198.183` على **نفس**
خادم AWS وقاعدة بياناته الحالية. هذا Elastic IP مخصص للبنية `aarast-host`،
وليس عنوانًا خاصًا أو نفقًا مؤقتًا. لا يحتاج الجوال إلى حل اسم DNS لهذا
الاتصال، ولا يتطلب شراء دومين أو إنشاء خدمة CloudFront.

## الشهادة والتشغيل

تدعم Let's Encrypt شهادات عناوين IP العامة ضمن ملف ACME `shortlived`؛ عمرها
160 ساعة. يحافظ Caddy الحالي `v2.10.2` على الشهادة ومفتاحها وتجديدها في
وحدة التخزين الدائمة `caddy_data`. لا توجد شهادة ذاتية التوقيع أو تعطيل
للتحقق من TLS. راجع [إعلان Let's Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability)
و[إعدادات Caddy TLS](https://caddyserver.com/docs/caddyfile/directives/tls).

يختار `default_sni` شهادة الـIP عندما لا يرسل عميل TLS اسم SNI. إصدار
الشهادة يستخدم HTTP-01 على المنفذ 80 عبر Caddy نفسه، والإعداد الجديد يوجّه
الـIP إلى `backend:3000`. تبقى المواقع القديمة للإدارة والموقع العام وروابط
الدعوات مستقلة كما كانت؛ تغيير API وحده لا يصلح DNS لهذه المواقع.

أضيف المتغير العام `AARAST_DIRECT_API_IP` إلى بيئة Caddy. يستخرج
`release.ps1` قيمته من مخرج CloudFormation الحالي `PublicIp` ويمرره إلى
`prepare-env.sh` كوسيط خامس. يحفظ المُهيئ الأسرار الموجودة، ويضيف هذا المتغير
مرة واحدة، ويرفض عنوانًا مختلفًا أو قيمة مكررة. العنوان لا يحل محل قيم
`AARAST_API_HOST` و`AARAST_ADMIN_HOST` و`AARAST_SITE_HOST` القديمة.

احتفظ بتخصيص Elastic IP؛ تحريره أو استبداله يحتاج مراجعة عنوان التطبيق.
يمكن الاحتفاظ بالتخصيص عند تغيير الجهاز الذي يستضيف التطبيق. لا تغيّر
العنوان إلى خادم آخر دون التحقق من هوية قاعدة البيانات.

## النشر المحدود الحالي

عملية 27 أكتوبر غيّرت Caddy فقط، بنفس الصورة المثبتة السابقة، ولم تشغّل
`deploy/aws/release.ps1` أو migrations أو إعادة بناء Backend/Admin. بقيت
معرّفات وأوقات بدء الحاويات العشر الأخرى كما كانت.

المصدر التطبيقي الجاري على AWS هو
`d27fa4dd23168f766d7a03d00e21a4218aec0f4d`. ملفات إعداد الاتصال الجديدة
المطبقة جرى التحقق منها ببصماتها، ولا تعني أن صور التطبيق أعيد بناؤها من
فرع الإصلاح غير المحفوظ في commit.

ملفات العملية الخاصة على الخادم تحت:

`/opt/aarast/operations/direct-ip-20261027/`

يحتوي `receipt.json` على بصمات المصدر ونتيجة مقارنة الحاويات. يحتوي
`rollback.json` على ملفات Compose السابقة ومجلدها ورقم إصدارها، ونسخة
البيئة السابقة في `env.before` محمية داخل هذا المجلد الخاص. لا تطبع ملف
البيئة أو تنقله إلى Git أو تقرير عام.

للعودة إلى إعداد البروكسي السابق، استخدم ملفات Compose الأصلية المسجلة
و`AARAST_RELEASE` المسجل، وأعد إنشاء خدمة `caddy` فقط مع `--no-deps`.
المصدر السابق لم يُكتب فوقه. لا تستعد قاعدة البيانات أو تشغّل whole-stack
deploy لعودة إعداد TLS، ولا تستعد بيئة قديمة فوق أسرار تغيرت لاحقًا دون
مراجعة. بقاء السطر العام الجديد في البيئة لا يضر الإعداد السابق الذي لا
يستهلكه.

## التحقق

- افتح `https://3.121.198.183/ready` من الجوال دون تحذير شهادة. أكد المالك
  نجاح هذا الاختبار من نفس الشبكة التي فشل فيها `sslip.io`.
- تحقّق أن SAN للشهادة يحتوي IP الصحيح وأن مصدرها العام موثوق. نجح
  Python TLS بالتحقق القياسي، دون تجاوز للأخطاء ودون SNI باسم دومين.
- يجب أن تكون `database` و`redis` و`media` و`openwa` كلها `up`.
- طلبات `{}` إلى `/api/v1/auth/login` و
  `/api/v1/auth/password-reset/request` يجب أن تعود بـ`400` من طبقة تحقق
  المدخلات؛ هذا يثبت وصول المسار، ولا يثبت دخول حساب أو تسليم OTP.
- افحص بمرور الوقت أن `notAfter` يتقدم بعد التجديد التلقائي. الإصدار الأول
  نجح؛ مرور دورة تجديد كاملة ليس نتيجة مثبتة يوم النشر.

اختبارات إعداد الاتصال:

```sh
node --test deploy/aws/direct-ip-contract.test.mjs
```

تشغّل الاختبارات صورة Caddy المثبتة محليًا دون شبكة، وتحلل إعداد Compose،
وتختبر المُهيئ على ملف بيئة مؤقت. يدعم `AARAST_ENV_FILE` تحديد هذا الملف؛
الافتراضي التشغيلي يبقى `/opt/aarast/app/.env`.

## بناء APK

نسخة الاتصال تعيد بناء نفس مصدر إصدار 25 أكتوبر مع
`AARAST_API_BASE_URL=https://3.121.198.183` ورقم بناء أعلى. لا تُبدّل كود
الواجهة أو مصدر Flutter الجاري الذي يعمل عليه وكيل آخر. احتفظ بهوية
الحزمة ومفتاح توقيع الإصدار السابق، ثم تحقّق من التوقيع والعنوان داخل APK
قبل تسليمه. إعدادات Firebase تبقى لنفس التطبيق والمشروع.

إذا شُغّلت اختبارات Flutter قبل Release، اسمح لأمر البناء القياسي بإعادة
توليد ملفات الإضافات بوضع Release. في SDK المحلي، استخدام `--no-pub` بعد
الاختبارات أبقى تسجيل `integration_test` ضمن ملف Java المولد، مع أن Gradle
يستثني هذه الإضافة من Release. لا تحذف التسجيل يدويًا ولا تغيّر SDK أو
dependencies لعلاج ملف مولد؛ استخدم أمر البناء القياسي وتحقق من ثبات
`pubspec.lock`.

العنوان القديم يبقى لنسخ APK المثبتة فعلًا وللإدارة/الموقع. سحب اسم API
القديم يكون بعد تأكيد انتقال المستهلكين إلى النسخة الجديدة؛ لا توجد محاولة
fallback تلقائية من التطبيق إلى الاسم الذي فشل.
