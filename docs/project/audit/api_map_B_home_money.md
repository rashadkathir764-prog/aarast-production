**Conventions for the proposed contracts**
- Base path `/api/v1`. `:planId` = wedding plan id. Money fields are decimal strings in the **plan currency** (`WeddingPlan.currency`, YER by default). A foreign-currency entry also carries `original{amount, currency, rate, rateZone, rateDate}`.
- Every write accepts `X-Client-Request-Id` (the existing `IdempotencyInterceptor`). Entities created offline also carry a `clientId`, which is unique per plan, so a replay returns the same row.
- Standard errors on every plan route: `404 PLAN_NOT_FOUND` (non-member, as today), `403 MONEY_PERMISSION_REQUIRED` / `TASK_…` / `GUEST_…`, `409 PLAN_ARCHIVED_READ_ONLY` (see the exemption list in §7.5), `409 PLAN_PAUSED`, `422 VALIDATION_FAILED`.
- "Owner only" means `plan.ownerUserId` (DEC 2026-10-11: funding sources and loans are owner only).

## 0. Cross-cutting decisions the design forces

### 0.1 The money formula (one formula, computed on the server)

Every number below comes from c01, b02, c05 and x08. They agree with one another:

| Term (UI) | Definition | Design value |
|---|---|---|
| «العرس بيكلفك» `committed` | Σ over active items of `expected`, where `expected = agreed total of the item's active costs` if any active cost exists, else `allocation` | 10 مليون (3 + 7) |
| «دفعت» `paid` | net payment ledger (payments − reversals − refunds received) | 4.6 |
| «باقي تدفع» `remaining` | committed − paid | 5.4 |
| «معك» `inHand` | received funding (including received parts of pledges) − paid | 7.5 − 4.6 = 2.9 |
| «موعود» `pledged` | Σ open pledge amounts not yet received | 1.2 |
| «ناقصك» `gap` | max(0, remaining − inHand) | 2.5 |
| «ومع الموعود» `gapIfPledges` | max(0, gap − pledged) | 1.3 |

**Backend today:** `summarizeFunding` sets `shortfall = confirmedCost − (received + pledged)`. That counts pledges (it equals the design's 1.3, not 2.5), and `confirmedCost` counts only costs, never allocations. 🔧 Replace it with the table above. Keep `availableCash` (= inHand).

**Visibility:** `inHand`, `pledged`, `gap` and `gapIfPledges` are derived from funding, so they are **owner only**. Everyone else who can see money gets `committed`, `paid` and `remaining`; the funding-derived fields come back as `null` with `fundingHidden: true`. The client must not try to recompute them.

### 0.2 Two sections: «الاتفاق مع أهل العروسة» and «عرسك»

- `section = AGREEMENT | WEDDING` on every money item (`BudgetCategory`).
- The **budget** (`WeddingPlan.estimatedBudget`, a07 «ميزانية عرسك … المهر محسوب لحاله») covers `WEDDING` only. `committed` adds both sections (c01 «العرس بيكلفك 10 مليون»). The reserve («الاحتياط», w19) is `budget − Σ WEDDING allocations`.
- **Plan direction:** for a groom plan, AGREEMENT is money paid out («سلّمت»). For a bride plan (JOURNEY_PROFILE: «استلمتِ، تستلمه»), the same section is money received. The server returns `agreement.direction = PAY | RECEIVE`. Received mahr is not a cost and is excluded from `committed` (see §9 issue 21).

### 0.3 The home projection is computed on the server

The home screen changes by moment (b01, b02, b04, b05, b07). The stage and every card on it are computed **on the server**, in one call, so that the phone, the widget (b09), the helper and a second device all show the same «الخطوة الجاية». Today the mobile app resolves the stage from the date (DEC 2026-08-09). The server becomes canonical, and the client keeps the same engine only for offline cold start.

`stage`: `SETUP` (fewer than all 4 setup steps done, b01) → `ACTIVE` (b02) → `WEEK` (7 days before the wedding up to the day before, b04/y12) → `DAY` (the wedding date in Asia/Aden, b05) → `AFTER` (from the day after, b07) → `ARCHIVED` (x13). `NO_DATE` (x01) and `PAUSED` (x24) belong to another audit part.

The next step is deterministic (DEC: Plan Pulse is "not AI"). Each next step carries a `whyCode` from a closed list, and the client renders the «ليش» text from it. Examples: `DUE_SOON_AND_FUNDED` («لأن موعدها قريب، والمبلغ في مدخراتك»), `LAST_UNCONFIRMED_PROVIDER` («آخر مزود ما أكّد»), `NEAREST_INSTALMENT` («أقرب قسط عليك»).

### 0.4 Which aggregates are computed where

| Aggregate | Where | Why |
|---|---|---|
| committed/paid/remaining/inHand/pledged/gap/gapIfPledges, section totals, reserve | **Server** (`money-summary`, `home`) | permissions (funding is owner only), one formula |
| monthly target «حط 450 ألف كل شهر» | **Server** | depends on gap, pledges and months left |
| pulse counts (tasks 12/30, guests 86/124, providers 3/6) | **Server** | contributor scoping already lives on the server |
| cash needed per night (b04) | **Server** | derived from schedules due at the event plus custody |
| custody balances (y04) | **Server** | the holder sees only their own |
| rafd totals (b05, b07, e09) | **Server** | the writer must not see totals (DEC:400) |
| cash flow by month (z03), impact chain (z01), weekly digest (z02), attendance forecast (w38/z06), peer benchmark (x03, b11) | **Server** | thresholds and the «ما نخمّن» rule |
| what-if simulation (c08) | **Server dry run** (`PUT money-budget?dryRun=true`) | avoids a second formula in the client |
| Hijri dates, prayer-time slot labels, amount in words («خمسمية ألف ريال»), countdown text | **Client** | presentation only |
| share text (c14), thanks text (e10) | **Client**, built from server data | the user sees the full text before sending |
| offline queue, «ينتظر الإرسال», undo bar (c04) | **Client** + idempotency on the server | |

## 7. Money domain model the design implies

### 7.1 Entities

```
WeddingPlan ──< MoneyItem (BudgetCategory) ──< Agreement (WeddingCost) ──< ScheduleLine (PaymentSchedule)
     │               section AGREEMENT|WEDDING        │                              │
     │               unit CURRENCY|GRAM               └──< Payment (CostPayment) >───┘
     │               allocation, coveredBy                   │   ├─ reversal (1:1, full)
     │                                                       │   └──< Refund (partial, n)
     │                                                       ├── fundingSourceId? / custodyAccountId?
     │                                                       └──< Receipt
     ├──< FundingSource (owner only) ──< LoanRepayment
     │        kind SAVINGS|FAMILY_SUPPORT|GIFT|LOAN|OTHER; status RECEIVED|PLEDGED|PARTIALLY_RECEIVED|WONT_ARRIVE
     ├──< CustodyAccount (one per holder) ──< CustodyMovement HANDOVER|SPEND|RETURN|ADJUST
     ├──< RafdEntry RECEIVED|GIVEN (gift book, social ledger)
     ├──< PlanEvent ──< ProgramItem
     └── reserve = budget − Σ allocation(WEDDING, active)    (derived, never stored)
```

| Concept | Design source | Rule |
|---|---|---|
| Budget | a07, w10, w19 | Covers WEDDING only. Can be null (x03). Changing it never changes allocations; the reserve absorbs the change and can go negative, which raises the warning `BUDGET_OVER_ALLOCATED`. |
| Money item (بند) | c02, c09, x15 | `allocation` is optional. `expected = agreed if any active agreement else allocation`. A GRAM item enters totals through `estimatedValue` only. `coveredBy` (FAMILY/OTHER) + allocation 0 = «خلّه بدون مبلغ». |
| Reserve (احتياط) | w18, w19 | Derived. Removing an item or lowering an agreement frees money into the reserve (c10 «أقل من بندك بـ 100 ألف»). |
| Agreement (اتفاق, cost) | c07, c10 | One item can hold several agreements (provider swap history). The total is fixed by the user. `capacitySeats` is used for a venue (z01). |
| Mahr agreement | a06, b02, c02, y08 | An item with `section=AGREEMENT, catalogKey=MAHR`, one active agreement, with deliveries recorded as payments. `direction` comes from the plan type (PAY for a groom, RECEIVE for a bride). Gold or the «شبكة» may sit in this section (§9 issue 20). |
| Schedule line | c03, c07, c10 | `dueAt` **or** `dueEventId` («يوم العرس»). It is a reminder only and contributes nothing until paid (DEC 2026-07-06). |
| Payment | c06, c11 | Append-only. Carries `paidBy`, `createdBy`, a source (funding **or** custody, at most one), and an optional foreign-currency snapshot. |
| Reversal | x14, w23 | Full amount, **once** (`reversalOfId` unique, as today). It is not allowed on a reversal, or on a payment that has refunds. It reopens the linked schedule line. The original row stays and is shown struck through. |
| Partial refund | w21, x11 | `0 < Σ refunds ≤ payment.amount`. `remainder = FORFEITED` keeps the rest as a cost of the item; `PENDING` makes a follow-up receivable with a reminder. A received refund returns to the chosen funding source (inHand goes up). |
| Receipt | w22 | Belongs to a cost and optionally a payment. Deleting a receipt never deletes the payment. |
| Funding source | c05, c12 | Owner only. `inHand = Σ received − paid from own money`. Payments from custody count as paid; a handover is not spending. |
| Pledge (موعود) | c05, x08, z03 | Never counted in `inHand` or `gap`; counted only in `gapIfPledges` and (with a date) in the cash flow. Resolution is §7.2. |
| Loan + instalments | c12, c13, b07 | A FundingSource with `kind=LOAN` and LoanRepayment lines. Writable and reminded on archived plans. |
| Custody (عهدة) | y03, y04, y05, z02 | The owner's money held by a helper. A handover moves money from the owner to a holder (inHand unchanged); a SPEND creates a Payment; a RETURN closes it. The holder confirms what they received. |
| Rafd (رفد) | b05, b06, e09, e10, x13 | Social ledger. RECEIVED cash entries feed a virtual funding line «الرفد» (received) for the owner. The book itself is not a funding source, so nothing is entered twice (§9 issue 39). |
| FX | c06, y02, y03 | Plan currency is canonical. A foreign entry stores `{amount, currency, rate, rateZone, rateDate}`. Rates are per zone (صنعاء/عدن) and dated. |

### 7.2 State machines

**MoneyItem:** `ACTIVE → REMOVED` (no payments; soft, kept in history; allocation goes to the reserve) · `ACTIVE → CANCELLED` (has payments; its agreements are cancelled; paid money becomes `refundExpected` or is forfeited) · `ACTIVE ↔ COVERED_BY_OTHERS` (allocation 0 + coveredBy). Hard delete is only for an item created by mistake that has no costs, payments or receipts (within 24 h).

**Agreement (WeddingCost):** `OPEN → PARTIALLY_PAID → PAID` (derived from the net ledger) · any state `→ CANCELLED` (pending schedule lines → CANCELLED; payments stay; `refundExpected = net paid − refunds − forfeited`). A cancelled agreement cannot take new payments (`409 COST_CANCELLED`) but can take refunds. Delete only when there are no payments (net or gross) and no receipts (today's rule; it is kept).

**ScheduleLine:** `PENDING → PAID` (through pay) · `PENDING → CANCELLED` · `PAID → PENDING` (when its payment is reversed) · `PENDING → DEFERRAL_REQUESTED → PENDING(new dueAt)` (z03).

**Payment:** `RECORDED → REVERSED` (terminal, once) · `RECORDED → PARTIALLY_REFUNDED → REFUNDED` (Σ refunds = amount). REVERSED and refunds are mutually exclusive.

**Refund:** `RECEIVED` (immediate) · remainder `PENDING → SETTLED | FORFEITED`.

**FundingSource (non-loan):** `PLEDGED → RECEIVED` · `PLEDGED → PARTIALLY_RECEIVED → RECEIVED` · `PLEDGED|PARTIALLY_RECEIVED → WONT_ARRIVE` (terminal for the unreceived part) · `PLEDGED --NOT_YET--> PLEDGED (nextCheckAt+7d)`.
**FundingSource (LOAN):** the same receipt states, then `REPAYING → REPAID` (all repayments PAID). When a LOAN pledge is received, the server answers `needsRepaymentPlan:true` and the client asks for the plan (fixes the x08 dead end).

**LoanRepayment:** `PLANNED → PAID | CANCELLED`; `PAID → PLANNED` only through an explicit undo with a reason.

**CustodyMovement (handover):** `PENDING_CONFIRMATION → CONFIRMED | DISPUTED → CONFIRMED(adjusted) | CANCELLED`. **CustodyAccount:** `OPEN → SETTLED` (balance returned or adjusted).

**RafdEntry:** `RECORDED → THANKED` · `RECORDED → VOIDED` (with a reason) · reciprocal `NONE → KNOWN(date|approx) → DUE → RETURNED`.

### 7.3 Rules (delete, cancel, reverse, refund)

1. Money history is append-only: payments, reversals, refunds and custody movements are never deleted (x14 «الدفعة ما تنمسح»).
2. Delete an item or agreement only if it has no payment rows **and** no receipts; otherwise answer `409 ITEM_HAS_PAYMENTS` with options (w23).
3. Reversal: full amount, once, needs a reason, records the actor; it is blocked when refunds exist.
4. A refund is partial or full; Σ ≤ payment; the remainder is FORFEITED or PENDING (w21); it is allowed on a cancelled agreement.
5. Swapping a provider never moves payments to the new party (§9 issue 31).
6. An allocation cannot go below the agreed total of the item (`ALLOCATION_BELOW_AGREED`).
7. Payment-level «خاصة بي» hides details (source, receipt, note) from others, never the amount (§9 issue 16).
8. Pledges never enter `inHand` or `gap`.
9. Funding, loans and pledges are owner only; the gap and inHand are owner only; custody is visible to the owner and to its own holder.

### 7.4 Who sees what (money)

| Data | Owner | Partner (bride or groom member) | Money view (q06) | Money manage | Custody holder | Rafd writer |
|---|---|---|---|---|---|---|
| committed/paid/remaining, items, agreements, schedules | ✓ | ✓ | ✓ | ✓ | – | – |
| inHand, pledged, gap, funding, loans, cash flow | ✓ | ✗ (DEC 2026-10-11) | ✗ | ✗ | ✗ | ✗ |
| custody, all holders | ✓ | ✗ | ✗ | ✗ | own account | – |
| rafd entries | ✓ | `canViewRafd` | `canViewRafd` | `canViewRafd` | – | own entries, no totals |

### 7.5 Archived and paused plans: exemptions from read-only

The design keeps these writable after archive (w13, x13, b07): rafd entries and reciprocals, thanks marks, loan repayments (pay and reminder settings), pledge resolution, refunds of pending remainders, custody settlement, provider reviews. Today **every** manage assertion blocks archived plans (`assertWeddingPlanWritable` in `permission.service.ts`). 🔧 Add a scoped `assertPlanWritableFor(purpose)` with an allow-list.

### 7.6 New capabilities

- `canWriteRafd` (DEC:400), `canViewRafd`.
- `CUSTODY_HOLDER`: implicit for a member who holds an open custody account. It allows confirming handovers and recording spends against items **without** seeing item totals or the plan money (the x06 «بدون أي رقم مالي» stays true except for their own custody balance).

## 11. Implementation order and risks

**Order**
1. **Decide the open design points** (§9 issues 1, 5, 6, 7, 10, 20, 21, 39) with the owner, because they change the formula and the samples.
2. **Money core**: the section and direction fields, the §0.1 formula in `money-summary`, payment `fundingSourceId`/`paidBy`/`createdBy`/`clientId`, the reserve, item soft removal and the w23 options, and `money-items` + composite item detail. This unblocks c01–c07, c09–c11, x03, x14, x15, w18–w20 and w22–w23.
3. **Mahr agreement** (a06 → AGREEMENT/MAHR item, `agreementLine`, y08 moment).
4. **Events + program + the home projection** (`GET /home` with stages SETUP/ACTIVE/WEEK/DAY/AFTER, `nextStep.whyCode`, moments + ack, booking reconfirmation, cash per event, schedule `dueEventId`). This unblocks b01–b05, b07, b12, b13, y06, y07, y09 and y12.
5. **Rafd book** (offline batch, writer and viewer permissions, the archive allow-list, thanks queue, reciprocals). This unblocks b05, b06, b07, e09, e10 and x13.
6. **Funding refinements**: pledge resolution, repayment plan, loan pay and reminders, partial refunds (x08, c12, c13, w21).
7. **Version 1.1**: custody + FX + expat (y02–y05), cash flow + deferral (z03), weekly digest + snapshots (z02), impact + undo (z01), search (y11), smart tasks (z05), attendance forecast + benchmarks (w38, x03).
8. **Later**: persistent AI consent with a limit of 30 (w36, w37 — can ship with 1.1 since it is small), quick-entry drafts (b03), receipt extraction (z04).

**Risks**
- **Data migration of money meaning:** existing plans may hold the mahr inside `estimatedBudget` or as an ordinary category. A migration must classify the AGREEMENT items, or ask the user once.
- **Formula change is visible:** `shortfall` today equals the design's «ومع الموعود». Changing it changes the numbers users already see; mobile and backend must ship together, behind a version field on `money-summary`.
- **Double counting:** father's direct payments vs «دعم الوالد», rafd vs GIFT sources, custody handovers vs spends. Each needs one source-of-truth rule and tests.
- **Privacy leaks:** `gap` and `inHand` reveal funding, so they are owner only. Search, digest, impact and share text must filter per viewer. Custody holders and rafd writers must not see totals.
- **Offline and idempotency:** rafd on the wedding day is many fast writes from several devices. It needs `clientId` uniqueness, a duplicate warning, and conflict UI (x19).
- **Archive exemptions** loosen a strong invariant (`PLAN_ARCHIVED_READ_ONLY`); keep the allow-list explicit and tested.
- **FX accuracy and legal position:** rates are informational, dated and per zone. The app never converts or moves money (DEC 2026-10-11); the copy must say «تقريبًا».
- **WhatsApp limits:** no bulk personal send without the Business API (e10, b04 reconfirm, z02); use deep links one by one.
- **AI data egress:** consent versioning, redaction of guest names and phones, audio retention, and a shared quota for Q&A, drafts and OCR.
- **Time and calendar:** Hijri display, prayer-time slots, Asia/Aden day boundaries for stages, moments, quotas and reminders.
- **Bride plans:** the direction flip of the agreement section touches every money screen; test both plan types from the start.
