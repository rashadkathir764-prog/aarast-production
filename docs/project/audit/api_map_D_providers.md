# API map D: providers (customer side + provider journey + admin)

Date: 2026-10-19. Static audit, no code changed.

**Rule:** the design is the reference (owner decision). The backend follows it later. Where a customer screen and `docs/project/PROVIDER_JOURNEY.md` disagree, this file lists the conflict in §5. It does not choose a winner unless the spec already decides.

**Inputs:** `docs/project/PROVIDER_JOURNEY.md` (abbreviated "PJ" below, with § numbers), `docs/project/research/reports/أعراس اليمن ومزودي الخدمات.md` ("research"), `docs/project/audit/screens_inventory.md`, `mobile/test/prototype/v3/*.dart` (screen functions), `docs/project/audit/api_inventory.md` ("inv"), and backend source checked directly (paths are relative to `backend/`).

**Legend:** ✅ an existing endpoint covers it as is · 🔧 an endpoint exists but needs a change · ➕ new endpoint or model. Paths without a host. App routes are `/api/v1/...` and back office is `/admin/...` (inv §0). "case" means one quote request and everything that follows it: offer, booking, deposit and review (PJ §4: «بطاقة وحدة لكل عرس»).

## 0. Backend facts verified in source (used throughout)

| # | Fact | Evidence |
|---|---|---|
| B1 | A provider is at most one confirmed booking per **calendar day**, enforced by a partial unique index. The booking has no slot, no unit and no quantity. | `prisma/migrations/20261015120000_add_bookings_and_provider_calendar/migration.sql` (`Booking_provider_confirmed_date_key ... | B2 | Every availability decision locks the provider row (`lockMarketplaceProvider(..., "UPDATE")`) inside a serializable transaction. If the index fires, the code maps P2002 to 409 `BOOKING_DATE_UNAVAILABLE`. | `src/marketplace/bookings.service.ts` `requestBooking`, `decideAsProvider`, `assertDayAvailable` |
| B3 | Blocking a day checks only CONFIRMED bookings and ignores REQUESTED ones. It uses `ownedProvider`, which skips the status check, so a SUSPENDED provider can block days. Unblocking takes no lock. | `bookings.service.ts` `blockDate` / `unblockDate` |
| B4 | A booking request needs the quote ACCEPTED. It runs `assertWeddingPlanWritable`, which blocks archived plans, but no "paused plan" status exists (`WeddingPlanStatus{PLANNING,ARCHIVED}`). | `bookings.service.ts` `assertCustomerAccess`; inv §2 planning |

| B6 | A request has one offer at most (`QUOTE_OFFER_ALREADY_EXISTS`). The offer is edited in place, with no version history. `WITHDRAWN` exists in the enum but nothing writes it. | B7 | Quote transitions: the requester can go from SENT/VIEWED to CANCELLED and from RESPONDED to ACCEPTED/REJECTED. The provider can go from SENT to VIEWED/REJECTED and from VIEWED to REJECTED. No EXPIRED status. The provider's decline and the customer's rejection both write `REJECTED`. Neither stores a reason. | `src/marketplace/quote-lifecycle.ts` `ALLOWED_TRANSITIONS` |
| B8 | Rejecting an expired offer throws `QUOTE_OFFER_EXPIRED`. A RESPONDED request cannot be cancelled. | `src/marketplace/quote-offer-rejection.ts:109`; B7 |

| B14 | In PLAN-scope conversations the provider side gets `counterpart = null`, so the provider sees no customer name. | `src/conversations/conversations.service.ts` ~l.964 |

**Order (model 1)**: REQUESTED → ACCEPTED (provider, stock check `inStock`) / DECLINED → READY → DELIVERED (provider or customer «تسلّمت») → COMPLETED. Either side can cancel before READY, and the customer can still cancel after READY with a reason.

**Hold**: ACTIVE → CONVERTED (booking or outside) | RELEASED (provider) | EXPIRED (job; notify `HOLD_RELEASED` to provider and, if `caseId` is set, to the customer).

**DepositMovement**: PENDING_COUNTERPARTY → ACKNOWLEDGED | DISPUTED. DISPUTED → ACKNOWLEDGED (counterparty changes their mind) or stays DISPUTED with an admin read-only view. Editing amounts after ACKNOWLEDGED creates a new movement plus a reversal (same ledger rule as finance).

### 4.3 Availability as shown to customers (PJ §1.3.6)

`remaining = Σ_resources(capacity − used)` for (day, slot), over the resources linked to the service. `state = BOOKED if remaining = 0 (or BLOCK covers it); ASK if now − calendarConfirmedAt > 14 d; LAST_ONE if remaining = 1 and total capacity > 1; else FREE`. Pending REQUESTED bookings never reduce `remaining`. Holds, outside bookings, blocks and confirmed bookings do. Vacation forces ASK/«في إجازة».

### 4.4 Double-booking guarantee

1. **Single counter per (resource, day, slot):** `SlotLoad(resourceId, day, slot, capacity, used)` with `CHECK (used >= 0 AND used <= capacity)`. A NAMED resource has capacity 1 and a POOL resource has capacity N. SINGLE-model services use the implicit NAMED resource, so model 2 and model 3 share one mechanism (PJ §1.2).
2. **Atomic claim:** inside a SERIALIZABLE transaction (existing `runSerializableTransaction`):
   - lock order: Conversation (existing quote lock order, B6/`quote-lifecycle.ts`) → Provider row (existing `lockMarketplaceProvider`) → SlotLoad rows ordered by (resourceId, day, slot) via `INSERT … ON CONFLICT DO NOTHING` then `SELECT … FOR UPDATE`;
   - release expired holds for those rows first (lazy expiry, so a stale hold never blocks a confirmation);
   - `UPDATE "SlotLoad" SET used = used + $q WHERE resourceId=$r AND day=$d AND slot=$s AND used + $q <= capacity`. A row count of 0 means 409 `BOOKING_CAPACITY_FULL` with `remaining`;
   - insert `Allocation(status=ACTIVE)` and set the booking status in the same transaction.
3. **Constraint backstop:** a partial unique index `Allocation(resourceId, day, slot) WHERE status='ACTIVE' AND exclusive` for NAMED resources. The CHECK on SlotLoad covers POOL resources.
4. **DAYS services** expand to one SlotLoad row per day × allowed slot (all of them for DAYS). They are claimed in sorted order inside one transaction, all or nothing.
5. **Capacity edits:** lowering a resource's quantity runs `UPDATE SlotLoad SET capacity=$new WHERE used <= $new` for future rows. Any failing row returns 409 `RESOURCE_CAPACITY_IN_USE {days}`.
6. **Release** (cancel, decline after confirm, hold expiry, block removal) decrements `used` under the same locks. A release is idempotent because the Allocation status is checked.
7. **Retry:** serialization failures (40001) are retried by the existing helper. P2002/P2010 or a CHECK violation maps to `BOOKING_CAPACITY_FULL`.
8. **Not guaranteed:** bookings the provider does not enter (paper or WhatsApp). Mitigation: the 14-day freshness rule plus the weekly «تقويمك صحيح؟» prompt.

### 6.2 Data migration from the current schema

1. Create one implicit NAMED `Resource` («الأساسي», quantity 1) per provider, and a ServiceResource for each active service. Every existing service becomes `model=SINGLE`, `durationType=NIGHT`, `allowedSlots=[NIGHT]`.
2. For each Booking with status CONFIRMED and a future day: set `slot=NIGHT`, `resourceId` = implicit resource. Insert SlotLoad (capacity 1, used 1) and Allocation(IN_APP, ACTIVE, exclusive). Past CONFIRMED bookings: `status=COMPLETED`, `completedAt = eventDate + 1 d` (no allocation needed).
3. For each ProviderBlockedDate with a future date: insert a CalendarBlock covering all slots, plus Allocations(BLOCK) and SlotLoads. Keep ProviderBlockedDate read-only for one release, then drop it.
4. **The existing partial unique index** `Booking_provider_confirmed_date_key ("providerId","eventDate") WHERE status='CONFIRMED'` must be dropped in the *same* migration that adds the Allocation unique index and the SlotLoad CHECK. Otherwise two CONFIRMED bookings in different slots (or on different units) on one day violate it. Until slots and units ship, keep it (it is still correct for day-level, single-resource providers). The order is: deploy new tables → backfill → switch writes to Allocation → drop the old index in the next migration.
5. QuoteOffer → OfferVersion v1 for each existing offer (lines empty, total = amount). `currentVersionId` backfilled.
6. QuoteRequest: `expiresAt = createdAt + 7 d`. Rows still SENT or VIEWED older than 7 days are set to EXPIRED by the first job run, not by the migration, so notifications are dedup-keyed. REJECTED rows where the actor was the provider (no offer exists) become DECLINED. With an offer they stay REJECTED.
7. ProviderReview: backfill `bookingId` from the user's COMPLETED booking with that provider (latest). Rows without one keep a null `bookingId` and are excluded from the unique index (partial unique `WHERE bookingId IS NOT NULL`).
8. Provider: `serves` from the categories' showForGroom/Bride (both → BOTH). `phoneVisible=true` for existing ACTIVE providers, which keeps current behaviour until they choose. `calendarConfirmedAt = null`, so availability shows «اسأل عن التوفر» until the first confirmation (honest default). `approvedAt = reviewedAt` for ACTIVE.
9. Ownership registry: add each new marketplace table to `architecture/ownership-registry.json` (L01). Finance/catalog/planning additions go to their owners. Add a pinned-migration entry for each new migration (L16).

## 7. Implementation order and risks

**Order** (each step behind the previous gate):

1. Decisions recorded: deposit recording approval (L17), booking-request expiry (L7), the event-audience filter (L33), rental boundary (L18), and whether deletion-driven cancels count (L29).
2. Privacy fixes that need no new model: B10 (strip phone and budget from the provider view unless shared), B11 (phone visibility, default true for existing providers), B13 (notification routes), B14 (counterpart name). Low risk, high value.
3. Account lifecycle: DRAFT, resubmit, reopen, field notes, vacation, and access policy changes so onboarding can write services before approval (p03 to p12). Admin moderation contracts.
4. Case lifecycle: DECLINED/EXPIRED/CLOSED, reasons, 7-day job, nudge, offer versions, withdraw, renew, and atomic accept plus booking request (p15 to p20, w31, x09, x10).
5. Calendar core: Resource, SlotLoad, Allocation, slots; outside bookings, holds, blocks, freshness; migrations §6.2 steps 1 to 4; capacity-checked confirm (p21, p28 to p32). The concurrency test suite comes first (two confirms racing, confirm vs outside booking, hold expiry vs confirm, DAYS range partial overlap).
6. Public availability (f02, f03, w30, x22, y13), the FREE/LAST_ONE/ASK/BOOKED logic and the alternatives endpoint.
7. Deposits (DepositMovement plus the finance event), cancel with refund, BookingChange plus planning events (p22 to p25, x11, c06, c10).
8. After the day: complete, not-happened, reviews per booking, reply, hide with reason (p26, p27, g04, w35, x12).
9. Model 1 (catalog, orders, ready, delivered) and model switching (p36).
10. Unclaimed claim links over WhatsApp, CSV import, verification documents (p41, p38, admin).
11. Home and performance aggregates (p13, p14, p39) last, because they read everything above.

**Risks**

| Risk | Why | Mitigation |
|---|---|---|
| Double booking during the index switch | The day-level unique index and the slot-level allocation must not both be authoritative with different meanings | Write to both until the cut-over; drop the old index only after all writers use Allocation; run a pre-drop consistency query |
| Lock-order deadlocks | New paths (outside booking, hold convert, BookingChange move) add SlotLoad locks after the existing Conversation → Request → Offer → Provider order | One shared `lockSlots(tx, keys)` helper, always sorted and always after the provider lock; deadlock test in CI |
| Cross-context coupling | Deposits touch finance, changes touch planning, events touch messaging and notifications | Public ports only (constitution L03/L04): finance emits `DEPOSIT_RECORDED`; marketplace never reads CostPayment |
| Privacy regressions | Removing phone and budget from provider responses may break the current mobile portal | Mobile portal is being replaced (PJ §9 «يتشال من الجوال»). Version the provider DTOs |
| WhatsApp claim links as a phishing vector | A link that says «عندك طلب» is attractive to spoof | Token-hashed, OTP phone match, no PII on the public page, rate limits |
| Hijri/Gregorian and slot boundaries | Riyadh/Yemen day boundaries already exist (UTC+3 in `booking-policy.ts`); slot times vary by region and prayer times | Slots are labels, not clock ranges; region-specific display only |
| Currency conversion misleads | Sanaa and Aden rials differ about 3× and Aden moves weekly (research) | Store original currency; display conversions marked «تقريبًا» with `asOf`; never convert stored offers |
| Stale calendars make "FREE" a lie | Providers manage paper and WhatsApp bookings | 14-day freshness, weekly prompt, ASK state, outside booking in 2 taps |
| Research gaps | Deposit norms, cancellation norms, studio team counts and hall multi-events are not documented (research conclusion) | Field interviews before freezing §6 (research table "ما يجب التحقق منه"); keep the model generic (POOL/NAMED) |
| Scope creep vs phase rules | AGENTS.md fences deposits, AI and confirmed bookings | L16/L17 decisions recorded first |
