# تصميم فحص أعرست بالكامل: المعنى، الرحلات، والقبول

- التاريخ: 2026-10-04.
- الحالة: تصميم لخطة فحص ومناقشة؛ لا يعتمد ميزات جديدة ولا يأذن بإصلاح أو نشر.
- المصدر المقروء: `14eccb50c6b2e050b044c7b00ac38a7e64f5164b`.
- الفرع: `staging/integration-decoupling-20261002`.

## 1. السؤال الذي نريد الإجابة عنه

هل تساعد أعرست كل شخص على إنجاز عمله داخل العرس، بحقيقة واحدة مفهومة، وصلاحيات صحيحة، وخطوة تالية واضحة، عبر الهاتف وAdmin والروابط؟

لا يكفي أن تعمل الشاشة، أو أن يعجبنا شكلها. نحتاج إثبات: لماذا توجد، من يحتاجها، ما الذي تعرضه، من أين تأتي الحقيقة، ماذا يتغير عند استخدامها، ومن ينتظر الخطوة التالية.

## 2. فهم المنتج الذي يبدأ منه الفحص

حسب [PRODUCT](../../project/PRODUCT.md) و[SCOPE_AND_PHASES](../../project/SCOPE_AND_PHASES.md)، مركز أعرست الحالي هو تنظيم خطة العرس ومالها ومهامها وضيوفها ومشاركتها. السوق والعروض والمحادثة المرتبطة بها يخدمان هذه الخطة. هذا وصف للنطاق المعتمد؛ ليس حكمًا بأن جميع رحلاته مكتملة.

| الشخص | العمل الذي يريد إنجازه | ما يجب أن يفهمه بعد كل خطوة |
| --- | --- | --- |
| زائر | يفهم قيمة التطبيق ويبدأ دون إرباك أو وعد غير متحقق | ما المتاح الآن وما يتطلب حسابًا |
| عريس / عروسة بصلاحية مالك | ينشئ خطة، يحدد ميزانية، ينظم التكاليف والدفع والمهام والضيوف، ويختار من يساعده | ماذا بقي، ما المدفوع فعلًا، وما القرار التالي |
| مشارك / مساهم | ينضم للخطة ويؤدي العمل المسموح ويعرف مسؤوليته | لماذا دخل، ماذا يستطيع فعله، وما الذي يبقى خاصًا |
| مزود | يقدم ملفًا صالحًا للاعتماد، ثم يتعامل مع طلبات عروض حقيقية | حالة اعتماده، الطلب الذي ينتظر رده، وما أرسله أو قبله العميل |
| Admin | يراجع ويعتمد ويدير المرجعيات والبلاغات ضمن صلاحياته | أثر القرار على المزود والعميل، وما سجلته العملية |
| شخص متعدد السياقات | ينتقل بين ملكية خطة ومساهمة ونشاط مزود دون اختلاط | من أنا الآن؟ أي خطة؟ وبأي صلاحية؟ |

العريس والعروسة ليسا افتراضًا بأن كل حساب يملك مال الآخر. وصلاحية المساهم ليست مستنتجة من اسم «مساعد». الحقوق الفعلية والعقد هما مصدر الحكم.

## 3. رأيي المبدئي كشريك، قبل النتائج

لو كان المشروع مشروعي، سأثبت الرحلات القائمة كاملة قبل توسيع دورة المزود إلى حجز وعربون واتفاقات جديدة. لا أريد للمستخدم أن يرى مجموعة أقسام لا يعرف أيها يبدأ به، أو أن يرى زرًا لا يستطيع إكماله، أو أن يفهم التذكير كأنه مبلغ مدفوع.

سأراجع الصفحة الرئيسية حسب الحالة والدور: ما القرار المناسب الآن؟ هل الكرت يقدم معلومة صحيحة وفعلًا مفيدًا؟ هل ترتيبه يوافق حاجة الشخص؟ سأبحث عن التكرار والضجيج، لكن لن أحذف عنصرًا لمجرد الذوق.

وفي المزودين سأفصل «ما ينفذه المنتج اليوم» عن «العلاقة المتكاملة التي نطمح إليها». التقييم والحجز والعروض والمال لا تُجمع بمجرد إضافة تبويبات. نحتاج تحديد من ينفذ الخطوة، ما الحالة المشتركة، وما الدليل الذي يجيز الانتقال. لا ننشئ كيانًا جديدًا قبل فهم الموجود.

هذه فرضيات توجيه للفحص؛ ليست findings مثبتة ولا تصميمًا معتمدًا.

## 4. ثلاث طبقات لا تختلط

1. **النطاق المعتمد:** الوثائق والقرارات الحالية، بما فيها الشروط والقيود.
2. **التنفيذ المثبت:** المصدر والعقد والاختبارات ذات الصلة، ثم المشاهدة الحية عند الحاجة.
3. **طموح المنتج:** اقتراحات المستخدم مثل مقارنة المزودين، الحجز، العربون، وأهلية التقييم بعد إكمال تعامل.

[مسودة علاقة المزود](2026-10-04-provider-engagement-product-design.md) و[خارطتها](../plans/2026-10-04-provider-engagement-roadmap-and-first-slice.md) مدخل للمقارنة، وليستا إذنًا بتنفيذ المراحل المستقبلية. غياب فكرة جديدة لا يصنف تلقائيًا عيبًا في العقد السابق.

القانون المالي الحالي مثال حاسم: قبول عرض خطة ينشئ تكلفة واحدة بمدفوع صفر؛ لا يسجل عربونًا أو دفعة أو حجزًا تلقائيًا. التذكير بالدفع ليس دفعًا ولا حجز رصيد.

## 5. وحدة الفحص

وحدة التغطية ليست اسم ملف أو route فقط:

**الشخص + السياق + مدخل الرحلة + الشاشة + القسم + العنصر + الحالة + الفعل + النتيجة + الطرف التالي.**

يشمل العنصر الكرت والزر والعداد والحقل والقائمة والنافذة والتنبيه والعنوان والحالة الفارغة. تجمع العناصر المتطابقة في قالب واحد فقط بعد إثبات أنها تشترك في المصدر والسلوك والصلاحية؛ تسجل كل مواضع استخدامها.

يجب أن يجيب سجل العنصر عن:

- الحاجة التي يخدمها، وسبب ظهوره لهذا الشخص الآن.
- البيانات أو الصيغة والوحدة والتوقيت ومصدر الحقيقة.
- من يراه ومن يعدله، وما يحدث عند سحب الصلاحية.
- الفعل المتوقع، وتأثيره، وتأكيده، وطريقة التعافي من الخطأ.
- الخطوة التالية والطرف الذي ينتظرها.
- الفرق بين تنفيذ موثق واختبار محلي وسلوك على هاتف وBackend منشور.
- قرار مسبب: إبقاء، إصلاح، تبسيط، دمج مقترح، إزالة مقترحة، إضافة مقترحة، أو غير مثبت.

## 6. معايير الحكم

| التصنيف | متى يستخدم؟ |
| --- | --- |
| BUG | سلوك خاطئ قابل لإعادة الإنتاج مقابل عقد معلوم |
| MISSING REQUIREMENT | مطلب معتمد صريح غير منفذ؛ يذكر مرجعه |
| ARCHITECTURE VIOLATION | مخالفة مباشرة مثبتة لقانون حالي أثناء تتبع رحلة؛ لا يفتح فحصًا معماريًا جديدًا |
| FALSE-GREEN GATE | اختبار/حارس مسؤول عن مخالفة محددة وأعطى نجاحًا خطأ، مع reproduction |
| UX FRICTION | يستطيع الشخص الإنجاز لكن الواجهة تزيد الغموض أو الخطوات أو احتمالات الخطأ؛ مع مشاهدة أو تسلسل محدد |
| INCONSISTENCY | جهتان أو موضعان يقدمان حقيقة/مصطلحًا/حالة متعارضة |
| PROPOSED SCOPE GAP | حاجة مقترحة غير معتمدة بعد؛ تحتاج قرار منتج |
| OPTIONAL IMPROVEMENT | تحسين ممكن ليس نقصًا إلزاميًا ولا blocker |
| NOT PROVEN | لا يوجد دليل كافٍ؛ يذكر ما ينقص الإثبات |

هذه امتدادات لوصف نتائج المنتج، ولا تستبدل تصنيفات [الدستور](../../../ARCHITECTURE_CONSTITUTION.md). التحسين الاختياري لا يعيد فتح المعمار.

الأولوية: P0 للخصوصية/فقد البيانات/الحقيقة المالية/التجاوز/نجاح وهمي؛ P1 لمنع رحلة أساسية؛ P2 للاحتكاك والتعارض؛ P3 للتحسين الاختياري. يراجع التصنيف بحسب الأثر الفعلي، لا اسم القسم.

## 7. النهج المختار

فحص واحد مترابط، في دفعات متتابعة: فهم العقد → جرد الأسطح → الرحلات الأساسية → انتقالات الأدوار → الحالات الصعبة → مراجعة كل عنصر → مصفوفة النقص → قرارات وأولويات.

بدائل لم نعتمدها:

- مراجعة الشكل أولًا: لا تفسر المال والصلاحيات وانتقالات الحالة.
- بناء نظام المزود المقترح أولًا: قد يكرر الموجود ويغير النطاق قبل قبول الأساس.

لا نحتاج إعادة تصميم المعمار. ولا نفحص كل حالة مع كل عنصر ضربًا حسابيًا بلا فائدة؛ نحدد الحالات المنطبقة ونبرر N/A.

## 8. حدود التنفيذ

- هذه المهمة تكتب الخطة والجرد الابتدائي فقط؛ الفحص الشامل لم ينفذ بعد.
- تنفيذ الفحص نفسه لا يصلح كودًا ولا يغير schema أو migrations أو deployment.
- لا Git mutation، لا commit، لا merge، لا main.
- لا وصول أو تغيير لمشروع Abdo أو الموارد أو أي مشروع آخر.
- لا إرسال OTP جديد أو إنشاء/حذف حساب أو اعتماد مزود أو تغيير عضوية ضمن مهمة التخطيط.
- مستقبلًا: كل عملية اختبار كتابية تحتاج نطاق بيانات اختبار واضحًا ومسموحًا؛ لا حذف حساب/بيانات مهمة أو تغيير اعتماد حقيقي لمجرد الفحص.
- تحفظ الأدلة الحساسة خارج Git، وتُحجب الهواتف والأكواد والتوكنات والمعرفات الخاصة.
- لا نتيجة عن خادم أو Release أو Push جهاز تستنتج من mock أو health 200.

## 9. تعريف نجاح الفحص لاحقًا

تغطية كل سطح وحالة منطبقة مصنفة، وكل رحلة لها نتيجة ودليل أو مانع صريح. لكل نقص: الأثر، السبب، مصدره، أقل علاج صحيح، قبول قابل للقياس، وتبعياته. لكل اقتراح توسعة: حاجة ومفاضلة وقرار مطلوب، دون تحويله إلى bug.

الناتج النهائي جواب شريك مفهوم: **ماذا أفعل أولًا؟ لماذا؟ ماذا أبقي؟ ماذا أبسط؟ ماذا ينقص فعلًا؟ وما الذي أؤجله؟** مع سجل يتيح مراجعة الاستنتاج، لا انطباع عام أو نسبة جودة مختلقة.
